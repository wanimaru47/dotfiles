# Create Issue スキル
 
GitHub issueの作成を、ヒアリングベースで補助するワークフロー。
単にissueを作るだけでなく、**フェーズの分離**（構想 vs 実装）と**関連issueの紐付け**を意識して、スコープの明確なissueを作成する。
 
---
 
## 概要フロー
 
1. **リポジトリ検出** — カレントディレクトリから自動検出
2. **親issue / 関連issueの確認** — 番号を聞き、内容を表示して確認
3. **紐付け種別の選択** — parent か related かをユーザーに選択してもらう
4. **issueの内容ヒアリング** — 目的・背景・スコープを聞き取る
5. **フェーズ判定と分割提案** — 構想と実装が混在していたらsub-issue分割を提案
6. **issue作成** — `gh issue create` で作成
 
---
 
## Step 1: リポジトリ検出
 
```bash
# リポジトリの存在確認
git rev-parse --is-inside-work-tree 2>/dev/null || echo "NOT_A_REPO"
 
# リポジトリ情報
gh repo view --json nameWithOwner,url --jq '.nameWithOwner + " (" + .url + ")"'
```
 
リポジトリが検出できない場合はエラーメッセージを表示して終了する。
 
---
 
## Step 2: 親issue / 関連issueの確認
 
ユーザーに「親issueや関連するissueはありますか？」と確認する。
 
### issueが指定された場合
 
番号またはURLから内容を取得して表示する：
 
```bash
# issueの内容を確認（番号 or URL）
gh issue view <NUMBER> --json number,title,body,state,labels --jq '{
  number: .number,
  title: .title,
  state: .state,
  labels: [.labels[].name],
  body: (.body | split("\n") | .[0:5] | join("\n"))
}'
```
 
取得した内容をユーザーに提示し、**正しいissueか確認**してもらう。
 
### 紐付け種別がない場合
 
ユーザーが「親issueも関連issueもない」と回答した場合は、Step 4 に進む。
 
---
 
## Step 3: 紐付け種別の選択
 
issueが確認できたら、**選択式**でユーザーに紐付け種別を選んでもらう。
 
提示する選択肢：
- **Parent（親issue）** — このissueの上位タスク。issue本文の冒頭に `Parent: #<NUMBER>` を記載する
- **Related（関連issue）** — 関連するが親子関係ではない。issue本文の冒頭に `Related: #<NUMBER>` を記載する
 
**複数のissueが指定された場合**: 各issueについて個別に parent / related を選択してもらう。
 
---
 
## Step 4: issueの内容ヒアリング
 
ユーザーからissueの内容を聞き取る。以下の観点で積極的に質問する。
 
### 必ず確認する項目
 
1. **何をしたいのか（目的）** — このissueで達成したいこと
2. **なぜやるのか（背景・動機）** — なぜ今これが必要なのか
3. **完了条件** — 何ができたらこのissueは閉じられるか
 
### 曖昧さへの対応
 
以下のような曖昧さを検知したら、必ず追加質問する：
 
- **スコープが広すぎる** → 「具体的にどの部分から着手しますか？」
- **完了条件が不明確** → 「何ができたら完了と言えますか？」
- **前提知識が不足** → 「〇〇について、現状はどうなっていますか？」
- **代替案の検討が不足** → 「〇〇という方法もありますが、検討しましたか？」
- **影響範囲が不明** → 「この変更による影響範囲はどこまでですか？」
 
### フェーズの意識
 
ヒアリング中、ユーザーの発言が**構想フェーズ**と**実装フェーズ**のどちらに属するかを常に意識する。
 
**構想フェーズの発言例:**
- 「〜を検討したい」「〜の方針を決めたい」「〜を調査したい」
- 「どういうアーキテクチャにするか」「要件を整理したい」
 
**実装フェーズの発言例:**
- 「〜を実装する」「〜のAPIを作る」「テストを書く」
- 「DBスキーマを変更する」「CIに組み込む」
 
---
 
## Step 5: フェーズ判定と分割提案
 
### 単一フェーズの場合
 
構想のみ、または実装のみであれば、そのままissue本文を生成する。
 
### フェーズが混在している場合
 
**構想と実装が混在したissueは作成しない。** 以下のように分割を提案する：
 
> このissueには構想（方針検討）と実装（コーディング）の両方が含まれています。
> フェーズを分けてissueを作成することを提案します：
>
> 1. **構想issue**: 〇〇の方針検討
> 2. **実装issue**: 〇〇の実装（構想issueの完了後に着手）
>
> まず構想issueから作成しましょうか？
 
ユーザーが承認したら、**再帰的にヒアリング**を行う：
- まず構想issueの内容を詰めて作成する
- 構想issueの作成後、実装issueのヒアリングに移る
- 実装issueの親issueは構想issueとする（または、元の親issueがあればそちらに紐付け、構想issueを related にする）
 
### issueが大きすぎる場合
 
単一フェーズ内でもスコープが大きい場合は、sub-issueへの分割を提案する：
 
> このissueのスコープが広いので、以下のように分割することを提案します：
>
> - 親issue: 〇〇（全体の概要）
> - Sub-issue 1: △△
> - Sub-issue 2: □□
>
> 親issueを作成してから、sub-issueを順に作成しましょうか？
 
承認されたら、親issueを作成後、各sub-issueについて再帰的にヒアリングと作成を行う。
 
---
 
## Step 6: issue本文の生成と作成
 
### issue本文のガイドライン
 
以下をガイドラインとしてissue本文を生成する。ユーザーの内容に応じて柔軟に調整してよい。
 
#### 構想issueの場合
 
```markdown
Parent: #<NUMBER>  <!-- 親issueがある場合 -->
Related: #<NUMBER>  <!-- 関連issueがある場合 -->
 
## 背景
 
（なぜこの検討が必要なのか）
 
## 検討したいこと
 
（検討すべきポイントの列挙）
 
## 構想方針
 
（現時点で考えている方向性。未定の場合は「このissueで決定する」と記載）
 
## 完了条件
 
- [ ] （方針が決定し、ドキュメントまたはissueコメントにまとまっている）
```
 
#### 実装issueの場合
 
```markdown
Parent: #<NUMBER>  <!-- 親issueがある場合 -->
Related: #<NUMBER>  <!-- 関連issueがある場合 -->
 
## 背景
 
（なぜこの実装が必要なのか。構想issueがある場合はリンク）
 
## やること
 
（具体的な実装内容）
 
## 実装方針
 
（技術的なアプローチ。決まっていない部分は明記する）
 
## 完了条件
 
- [ ] （具体的な完了チェックリスト）
```
 
### issue本文の確認
 
生成したissue本文は**必ずユーザーに確認**してもらってから作成する。
 
### 作成コマンド
 
```bash
# gh CLI の存在確認
gh --version || echo "gh CLI not found"
 
# issue 作成
gh issue create \
  --title "<タイトル>" \
  --body "<本文>"
```
 
### 作成後
 
- 作成されたissueのURLを表示する
- sub-issueがある場合は、次のsub-issueのヒアリングに移る
- すべてのissue作成が完了したら、作成したissue一覧をまとめて表示する
 
---
 
## エラーハンドリング
 
| 状況 | 対処 |
|------|------|
| リポジトリが検出できない | エラーメッセージを表示して終了 |
| `gh` CLI がインストールされていない | インストール方法を案内 |
| 指定されたissue番号が存在しない | 番号の再確認を求める |
| `gh` の認証が切れている | `gh auth login` を案内 |
 
---
 
## 重要な注意事項
 
- **フェーズの混在を許容しない**: 構想と実装が混ざったissueの作成は避け、必ず分割を提案する
- **積極的に質問する**: 曖昧な点を放置せず、具体化のための質問を行う
- **ユーザーの確認を取る**: issue本文は必ず確認後に作成する
- **ラベル・アサイニー・マイルストーンは扱わない**: issue本文と紐付けに集中する
- **再帰的なヒアリング**: sub-issue分割時は、各sub-issueについて個別にヒアリングを行う
