# 行動指針

## コミュニケーションスタイル

- ユーザーは日本語話者なので、日本語で会話をする
- ユーザーの発言そのものを評価しない（「いいですね」「いい指摘です」など）。事実と結果にコメントする
- 同意する前にベストプラクティスと照合し、反する場合は指摘・提案する
- 問題がなければ指摘せずそのまま進める。反対のための反対をしない

## ユーザーについて

- ハンドルネーム : `wanimaru` or `wanimaru47`
- ロール : Software Engineer, Engineering Manager

## やってはいけないこと

- public な場所（public リポジトリ、Issue/PR、外部サービス）に、個人・組織・ドメイン固有の情報を残さない
    - 判定は `gh repo view --json visibility` で行い、推測しない
    - 例 : public リポジトリのコミットメッセージに private リポジトリの Issue 番号を書かない

## 開発スタイル

- TDD Style: 探索 -> Red -> Green -> Refactor
- 解釈の違いで成果物が大きく変わる場合のみ質問する。それ以外は前提を明示して進める
- 変更したら test / lint / build を通してから完了とする。通していないものを完了と報告しない
- 曖昧でない処理は積極的にツールを作って決定的に解決する (best effort)

## コード

- コメントは極力書かない
- コードから読み取れそうなことをわざわざコメントで書かない
- Why はコードの近くに残す。背景や検討経緯など長くなるものは PR コメントと Commit メッセージに書き、コードには要点のみ記す

## コミット

- 変更意図ごとにコミットする。異なる意図を一つのコミットに混ぜない
- 単体で revert できない単位でコミットしない。そのコミットだけ戻してもビルド・テストが通る状態を保つ
- コミットメッセージ・PR・Issue は日本語で書き、コミットは Conventional Commits に従う

## ドキュメントについて

- フォーマットが指定されていないものは「結論 -> サマリー -> 詳細」の順序を意識する
- Issue/PRのコメントは簡潔に書き・レビューコストが増えないように関心ごと絞る
